# Тестовые данные и учётные записи для API-проверки

## Что подготовлено

| Файл | Содержимое |
|---|---|
| [api-check-data.json](../data/api-check-data.json) | Синтетические данные одного полного сценария: знание, вопрос, отклик, два сообщения, результат и восстановление профиля. Тела запросов связаны с шагами DATA-API по имени. |
| [api-test-accounts.json](../data/api-test-accounts.json) | Две роли, локальные аккаунты, способы входа и имена переменных сессий. Рабочих секретов и персональных MAX ID нет. |
| [DATA-API.yaml](../DATA-API.yaml) | Порядок 26 проверок, методы, параметры, сохранение значений ответов, ожидаемые коды и JSON-схемы. |

Формат JSON-набора — `1.0`, идентификатор — `synapse-education-help-v1`. Все тексты вымышлены и не подтверждают реальный опыт участника. Это данные запросов, а не дамп БД: начальное заполнение их не импортирует. При выполнении шагов API создаёт записи и назначает UUID.

## Учётные записи и роли

| Роль | Локальный аккаунт | Публичный API MAX | Действия |
|---|---|---|---|
| Автор (`author`, `author_login`) | Анна, `persona: anna` | Первый реальный тестовый аккаунт MAX | Создать вопрос, выбрать помощника, завершить диалог |
| Помощник (`helper`, `helper_login`) | Борис, `persona: boris` | Второй реальный тестовый аккаунт MAX | Добавить знание, найти вопрос, откликнуться и ответить |
| Аноним (`anonymous`) | Не требуется | Не требуется | Прочитать доступные данные, проверить отказ в доступе к профилю |

`author_login` и `author` — один участник до и после входа; аналогично для помощника. Модератор и администратор обязательному сценарию не нужны. Роль в сценарии не создаёт дополнительных полномочий: один человек может и спрашивать, и помогать.

Анна и Борис автоматически создаются после `bash scripts/jury.sh up`. Логинов и паролей приложения нет. На публичном сервере эти demo-аккаунты отключены: два реальных аккаунта MAX нужно предоставить отдельно, а профиль приложения появится при первом успешном MAX-входе. JSON-файл сам по себе не создаёт аккаунты в мессенджере.

Перед прогоном нужны два разных выделенных участника без открытых вопросов, активных диалогов и взаимных блокировок. Активные знания помощника должны быть пустыми — это проверяет шаг `helper_profile`. Не используйте профиль с рабочими знаниями: шаг `add_knowledge` временно заменяет его редактируемые поля. Оба участника должны ознакомиться с правилами и согласиться принять их в рамках проверки.

## Получить авторизованную сессию

### Локальная проверка

Запустите `bash scripts/jury.sh up`. По адресу `http://localhost:18080` выполните два запроса:

```http
POST /api/auth/demo
Content-Type: application/json

{"persona":"anna"}
```

```http
POST /api/auth/demo
Content-Type: application/json

{"persona":"boris"}
```

Ответ каждого входа: HTTP `200`, JSON с полями `token`, `expiresAt` и `user` (`id`, `displayName`, `provenance`). Сохраните `token` Анны как `AUTHOR_TOKEN`, Бориса — как `HELPER_TOKEN`, а `user.id` — как `AUTHOR_ID` / `HELPER_ID`. Эти UUID должны различаться.

Для локального воспроизведения DATA-API используйте этот адрес вместо публичного HTTPS и замените **только** запросы `login_author` / `login_helper` на два запроса выше. Остальные шаги и ожидаемые JSON-структуры остаются теми же. Такой прогон проверяет данные и бизнес-сценарий, но не реальную авторизацию MAX.

### Публичная проверка через MAX

1. Заполните HTTPS-адрес в `DATA-API.yaml`. Каждый из двух участников открывает mini-app из подключённого бота в своём MAX. В открытом режиме дополнительные разрешения не нужны; для закрытого пилота оператор включает оба MAX ID в `PILOT_ALLOWED_MAX_IDS`.
2. В веб-клиенте MAX откройте инструменты разработчика → Network, выберите запрос mini-app `/api/auth/max`. Из **тела запроса** возьмите значение `initData` без изменения строки. Это исходное значение `window.WebApp.initData`: не `initDataUnsafe`, не весь JSON-запрос и не Bearer-токен из ответа.
3. Передайте строки в приватные переменные HTTP-клиента `MAX_INIT_DATA_AUTHOR` и `MAX_INIT_DATA_HELPER`. Шаги входа отправят их на тот же сервер:

```http
POST /api/auth/max
Content-Type: application/json

{"initData":"<исходная подписанная строка данного аккаунта MAX>"}
```

4. Ожидаются HTTP `200` и та же структура сессии, что выше. Шаги `capture` сохранят токены и UUID. Для защищённых запросов используйте `Authorization: Bearer <token>` соответствующего участника.

В стандартной конфигурации возраст `initData` и срок сессии ограничены 3600 секундами; срок выданной сессии указан в `expiresAt`. На `401` заново откройте mini-app и получите свежий вход. На `403` проверьте режим доступа и необходимость принятия правил. `POST /api/auth/logout` отзывает переданную сессию. Токен бота и пароль БД для проверки не нужны.

## Загрузить данные и пройти сценарий

Используйте HTTP-клиент с переменными или исполнитель платформы, адаптированный к формату DATA-API. Файлы JSON и YAML описывают данные и проверки; готовый универсальный исполнитель в комплект не входит.

1. Выполните `ready`, `catalog`, `read_rules`, `deny_anonymous_profile`. Сохраните текущие `TAXONOMY_VERSION` и `RULES_VERSION` из ответов. Тема `pathways.admissions.program_choice` должна быть активной.
2. Войдите двумя участниками и выполните принятие правил текущей версии. Прочитайте профиль помощника: сохраните его имя, описание, доступность, ёмкость и ревизию по `capture`.
3. Для каждого нового прогона создайте UUID v4 из `generated_variables`. Например, генерация одного UUID: `node -e 'console.log(require("node:crypto").randomUUID())'` (Node.js 24 нужен только для этого необязательного примера).
4. Последовательно выполните остальные `mandatory_checks`. Для запроса с телом возьмите объект `request_bodies_by_check.<id шага>` из JSON-набора. Подставьте `${NAME}` из входных переменных или предыдущих ответов. Отдельное значение сохраняет тип: `HELPER_AVAILABLE` — boolean, `HELPER_CAPACITY` — число. Остальные параметры и заголовки берутся из DATA-API.
5. После `add_knowledge` у помощника одно знание; после `create_draft` черновик виден только автору. Публикация делает вопрос доступным в ленте помощника. Если первая страница не содержит вопрос, продолжайте `GET /api/requests?scope=feed&limit=50&after=<nextCursor>` до совпадения или конца списка.
6. После отклика и выбора помощника появляется один диалог. Обе стороны читают сообщения друг друга. `close_with_result` сохраняет `outcome: helpful` и следующий шаг; вопрос получает `status: resolved`, диалог — `status: closed`.
7. Выполните `restore_helper_profile`, затем оба `logout`. Исходные редактируемые поля помощника восстановлены, активные знания снова пусты, выданные проверке сессии отозваны. История вопроса, два сообщения, результат и согласие с правилами остаются в БД.

Идентификаторы вопроса, отклика, диалога и сообщений всегда берутся из ответов этого прогона. Не фиксируйте UUID и версию каталога вручную. `If-Match` содержит текущую ревизию в кавычках, например `"0"`. Для повтора того же действия после сетевой ошибки сохраняйте его `Idempotency-Key`, а для повтора того же сообщения — `clientMessageId`.

## Повторный прогон и передача доступа

Прогоны выполняются последовательно: Анна и Борис общие для одной локальной БД, параллельное редактирование может дать конфликт ревизии. После успешного прогона повторите сценарий с новыми UUID; старые записи останутся как история проверки.

Если проверка прервалась, сохраните идентификаторы созданных ресурсов. До выбора помощника отмените тестовый вопрос через mini-app или `/api/requests/{id}/cancel`; после выбора завершите диалог через `/api/conversations/{id}/close` с `outcome: no_result`. Восстановите исходный профиль помощника с актуальной ревизией и отзовите оставшиеся сессии. Лимит — три открытых вопроса автора; незавершённые предыдущие прогоны могут мешать следующему. Удалять БД для повторения не требуется.

В публичный комплект входят JSON-данные, паспорта ролей, DATA-API и эта инструкция. Ссылку на бота, HTTPS-адрес и назначение двух реальных MAX-аккаунтов участникам проверки согласуйте отдельно. Для полного DATA-API-прогона передаются свежие `initData` обоих участников; готовые Bearer-сессии подходят для отдельных ручных запросов, но не заменяют входные `MAX_INIT_DATA_*`. Передавайте их приватно непосредственно перед проверкой; не помещайте в Git, снимки экрана и журналы. Для локальных файлов с доступом предусмотрен исключённый из Git каталог `submission-private/`.
