# API Синапса

API реализует тот же профиль и путь помощи, которым пользуются бот и mini-app: вопрос → адресный подбор → отклик → выбор помощника → личный диалог → результат.

Машинный контракт: [openapi.json](../openapi.json), OpenAPI 3.1, API `0.12.0`. Версионная копия - [contracts/openapi.v0.12.json](../contracts/openapi.v0.12.json). Адрес действующего HTTPS-экземпляра передаётся вместе с материалами сдачи; в репозитории нет его секретов или пользовательских сессий. В инструменте работы с OpenAPI задайте URL нужного экземпляра вместо локального `servers.url`.

## Два способа получить доступ

| Режим | Вход | Адрес |
|---|---|---|
| Локальная проверка | `POST /api/auth/demo`, вымышленные участники `anna` / `boris` | `http://localhost:18080` после `bash scripts/jury.sh up` |
| Действующий экземпляр MAX | `POST /api/auth/max`, подписанная строка `initData` своего пользователя MAX | HTTPS-origin, выданный командой |

Учебные аккаунты предназначены только для отдельной локальной БД. На production endpoint `/api/auth/demo` запрещён. Токен бота не является пользовательским API-токеном и проверяющим не выдаётся.

### Локальная сессия

Тело запроса:

```http
POST /api/auth/demo
Content-Type: application/json

{"persona":"anna"}
```

Для второго участника замените `anna` на `boris`. Ответ содержит `token`, `expiresAt`, `user.id`, `user.displayName`, `user.provenance`. Передавайте `token` в следующих запросах как `Authorization: Bearer <token>`.

Например, с Node.js 24 можно получить сессию и прочитать профиль, не выводя токен:

```bash
node --input-type=module <<'JS'
const base = 'http://localhost:18080';
const login = await fetch(base + '/api/auth/demo', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ persona: 'anna' }),
});
if (!login.ok) throw new Error('Login HTTP ' + login.status);
const session = await login.json();
const response = await fetch(base + '/api/profile', {
  headers: { Authorization: 'Bearer ' + session.token },
});
if (!response.ok) throw new Error('Profile HTTP ' + response.status);
console.log(await response.json());
JS
```

Node.js нужен только для этого необязательного примера. Контейнерный запуск и HTTP-клиент жюри от него не зависят. Пример показывает вызовы API; он не свидетельствует о проведённой проверке текущей поставки.

### Сессия настоящего пользователя MAX

1. Откройте mini-app через бота в своём MAX-аккаунте. У приложения должен быть именно контекст запуска MAX, а не отдельная обычная вкладка с тем же URL.
2. Mini-app получает `window.WebApp.initData` и отправляет исходную строку без изменений в `POST /api/auth/max`:

```json
{"initData":"<исходная подписанная строка запуска MAX>"}
```

3. Сервер проверяет подпись и срок данных запуска, создаёт или находит профиль и выдаёт сессию. В открытом режиме вход разрешён любому подлинному аккаунту MAX.
4. Для ручной работы с внешним HTTP-клиентом в веб-версии MAX откройте инструменты разработчика, выберите контекст мини-приложения и найдите ответ своего запроса `/api/auth/max` во вкладке Network. Перенесите `token` только в приватное хранилище секретов своего HTTP-клиента. Это текущая пользовательская сессия, не постоянный ключ. Не публикуйте ответ целиком, HAR-файл или снимок токена.

Обычному пользователю эти действия не нужны: mini-app выполняет вход автоматически. Отдельной кнопки выгрузки API-токена и бессрочных ключей в этой версии нет. На устройстве без инструментов разработчика для API-проверки используйте веб-клиент MAX или локальные учебные роли.

Сессия по стандартным конфигурациям действует 3600 секунд; фактический срок находится в `expiresAt`. На `401` откройте mini-app заново и получите новую сессию. `POST /api/auth/logout` с текущим Bearer-токеном отзывает именно эту сессию; работа внешнего клиента с ней также прекратится. Нет административного ключа, позволяющего выдавать себя за другого участника.

## Основные группы методов

| Область | Методы |
|---|---|
| Доступность и настройка клиента | `GET /health/live`, `/health/ready`, `/api/bootstrap` |
| Темы и контекст | `GET /api/taxonomy` |
| Правила | `GET /api/community-rules`, `GET /api/community-rules/status`, `POST /api/community-rules/accept` |
| Свой профиль | `GET`, `PUT /api/profile` |
| Вопросы и подбор | `GET`, `POST /api/requests`; чтение/редактирование заявки; `/publish`, `/cancel`, `/reach` |
| Отклики | `/api/requests/{id}/offers`, `/api/offers/{id}/accept`, `/withdraw` |
| Переписка и результат | `/api/conversations`, `/api/conversations/{id}/messages`, `/close` |
| Безопасность общения | `POST /api/blocks`, `POST /api/reports` |
| Уведомления | `GET`, `PUT /api/notification-settings` |
| Модерация | `/api/moderation/access`, `/api/moderation/reports` и действия по жалобе |

Точные тела, параметры, статусы и структуры ответов приведены в OpenAPI. `/webhooks/max` предназначен для подписки MAX и использует отдельный секрет; это не обычная пользовательская точка входа API.

## Правила вызовов

- Перед действиями общения прочитайте `GET /api/community-rules` и явно примите именно возвращённую версию через `POST /api/community-rules/accept` с телом `{"version":"<полученная версия>"}`. Автоматическое принятие от имени жюри не выполняется.
- При изменении профиля или черновика передавайте `If-Match` с текущей ревизией в кавычках, например `"3"`. При конфликте перечитайте актуальное состояние.
- Для операций, где контракт требует `Idempotency-Key`, используйте новый UUID на новое действие и тот же UUID только для повтора того же действия с тем же телом. У сообщения собственный `clientMessageId`.
- UUID заявок, откликов и диалогов берутся из предыдущих ответов. Не используйте идентификаторы одного экземпляра в другом.
- Компетенции и вопросы используют только активные темы L2 и глубже из актуального каталога. Каталог содержит два активных L1: образование и карьера. `archivedCompetencies` доступны только для чтения и не отправляются в `PUT /api/profile`.
- Сессия принадлежит одному пользователю. Просмотр чужой переписки запрещён; отсутствие доступа может возвращать `404`, чтобы не раскрывать существование ресурса.
- Роль модератора задаётся оператором через `MODERATOR_MAX_IDS`; обычный пользователь и учебные аккаунты не получают её автоматически.
- Клиентские HTTP-вызовы выполняются с того же origin, что и mini-app. Для внешнего HTTP-клиента браузерный CORS не требуется; открытый CORS в продукте не заявлен.

## Сценарий воспроизведения

1. Участники A и B входят и принимают правила. Локально A - Анна, B - Борис; на MAX это два отдельных реальных аккаунта.
2. B добавляет активную компетенцию, готовность помогать и подходящий контекст. Не перезаписывайте существующий профиль реального человека демонстрационными данными.
3. A создаёт и публикует вопрос по этой теме.
4. B получает вопрос в адресной ленте `scope=feed` и предлагает помощь.
5. A принимает отклик. Стороны получают общий диалог и обмениваются сообщениями.
6. A завершает диалог и фиксирует результат и следующий шаг.
7. Участники меняются сторонами: тот же профиль может спрашивать об одном и помогать в другом.

Набор синтетических сюжетов находится в [data/demo-scenarios.json](../data/demo-scenarios.json). Он описывает примеры, а не автоматически созданные вопросы и переписки: свежая локальная база содержит учебные профили и каталог, а действия выполняются через интерфейс или API.

## Комплект автоматической оценки

OpenAPI - контракт HTTP API. Он не заменяет отдельный `DATA-API.yaml`, параметры сценариев, данные и роли, которые запрашивают организаторы.

[DATA-API.yaml](../DATA-API.yaml) содержит обязательные проверки в формате проекта `1.0`. [Подготовленные JSON-данные](../data/api-check-data.json) и [паспорта тестовых ролей](../data/api-test-accounts.json) соответствуют этим шагам; порядок загрузки, локальные аккаунты и получение сессий MAX описаны в [инструкции API-проверки](API_TEST_DATA.md).

Для публичного сценария входные `MAX_INIT_DATA_AUTHOR` и `MAX_INIT_DATA_HELPER` — исходные подписанные строки запуска двух аккаунтов, а не уже выданные Bearer-токены. Их можно взять из тела своего запроса `/api/auth/max` в Network веб-клиента MAX. HTTPS-адрес заполняется в DATA-API; реальные данные входа и краткоживущие сессии передаются приватно и не коммитятся.
