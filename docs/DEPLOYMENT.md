# Развёртывание Синапса

Для знакомства с продуктом используйте [локальный запуск для жюри](LOCAL_RUN.md). Этот документ описывает сервер с настоящими пользователями MAX. Серверный и учебный режимы используют разные базы и конфигурации.

## Что потребуется

- Linux, Bash, Docker Engine с Compose v2.20+, `flock` из util-linux; доступ к образам и пакетам для первой сборки.
- Публичный HTTPS-адрес на порту 443, направленный на сервер; обратный прокси перед приложением.
- Токен и имя вашего бота MAX; права указать URL мини-приложения в его настройках.
- Публичная цепочка доверенных сертификатов MAX API в `private/max-ca.pem`.

Токены, пользовательские ID, пароли БД и адрес действующего экземпляра не включены в эту копию. Получение доступа к готовому экземпляру и его ссылка передаются проверяющим отдельно.

## Первая установка

Все команды выполняются из корня проекта. Отдельные Node.js и C++ на сервере не требуются: сборка и служебные команды работают в контейнерах.

### 1. Приватные настройки

Создайте каталог и файл; если файл уже существует, сохраните его содержимое:

```bash
mkdir -p private
touch .env.max.local
chmod 600 .env.max.local
```

В локальном редакторе заполните `.env.max.local`:

```dotenv
MAX_BOT_TOKEN=REPLACE_WITH_BOT_TOKEN
MAX_BOT_USERNAME=REPLACE_WITH_BOT_USERNAME
```

Укажите реальные значения своего бота; имя без `@`. Файл исключён из Git. Не передавайте токен аргументом команды и не включайте его в скриншоты или документацию.

Подготовьте `private/max-ca.pem` из публичных PEM-сертификатов, указанных в [официальной документации API MAX](https://dev.max.ru/docs-api/methods/GET/me). Файл должен читаться процессом контейнера; для публичного файла CA допустимы права `644`. Это доверенные сертификаты API, а не закрытый ключ HTTPS-сервера. Проверка TLS остаётся включённой.

Затем запустите интерактивную подготовку:

```bash
bash scripts/pilot.sh prepare --prompt
```

Укажите настоящий HTTPS-адрес без дополнительного пути, имя бота и режим `public`. Будет создан `.env.pilot.local` со случайными паролем БД и webhook secret. Существующий файл команда не перезаписывает.

Основные параметры `.env.pilot.local`:

| Параметр | Назначение |
|---|---|
| `APP_PUBLIC_URL` | Публичный HTTPS-origin мини-приложения и API |
| `PILOT_MODE=false` | Доступ любому пользователю с подтверждённым входом MAX |
| `PILOT_ALLOWED_MAX_IDS` | Учитывается только при `PILOT_MODE=true`; при открытом доступе не нужен |
| `PILOT_PORT=8085` | Локальный порт backend для обратного прокси |
| `MAX_BOT_TOKEN`, `MAX_BOT_USERNAME` | Настройки вашего бота |
| `MAX_WEBHOOK_SECRET` | Секрет проверки входящих событий MAX |
| `POSTGRES_PASSWORD` | Пароль отдельной базы серверного экземпляра |
| `MODERATOR_MAX_IDS` | MAX ID назначенных модераторов; пустое значение отключает доступ к модерации |
| `MAX_PRODUCT_NOTIFICATIONS_ENABLED` | Глобальное разрешение дополнительных уведомлений; по умолчанию `false` |

Для модерации назначьте хотя бы одного ответственного пользователя. Общий вход не выдаёт права модератора. Дополнительные уведомления требуют одновременно глобального разрешения, согласия пользователя и действующего диалога с ботом; ответы на команды бота этим флагом не отключаются.

### 2. HTTPS и запуск

Backend публикуется только на `127.0.0.1:8085`, PostgreSQL наружу не публикуется. Настройте свой прокси на этот адрес. Для Caddy, установленного **на том же Linux-хосте**, есть [пример конфигурации](../infra/Caddyfile.pilot.example): замените домен своим и примените конфигурацию службы. Прокси в отдельном контейнере требует другого сетевого адреса backend.

```bash
bash scripts/pilot.sh deploy
```

Команда собирает образ, запускает БД, останавливает backend/worker на время обновления, сохраняет резервную копию, применяет миграции и каталог, затем запускает backend и worker. Тесты по умолчанию не запускаются; компиляция и проверки готовности сервисов остаются. Для полной сборки с тестами существует `deploy --with-tests`.

### 3. Подключение MAX

1. Привяжите `APP_PUBLIC_URL` к мини-приложению своего бота через доступные настройки MAX или процедуру организаторов.
2. После настройки HTTPS выполните:

```bash
bash scripts/pilot.sh connect
```

Команда проверяет совпадение настроек с запущенными контейнерами, регистрирует webhook `/webhooks/max` и меню команд. Регистрация webhook и настройка URL mini-app - отдельные операции.

3. Передайте пользователям ссылку своего бота. Пользователь открывает бота, отправляет `/start`, открывает мини-приложение и принимает правила. При `PILOT_MODE=false` список приглашённых не требуется.

Открытие URL mini-app в обычном браузере без данных запуска MAX не подтверждает личность. Учебный вход на сервере отключён: `APP_ENV=production`, `DEMO_MODE=false`.

## Обновление существующего экземпляра

После получения нужной версии исходников:

```bash
bash scripts/pilot.sh access public
bash scripts/pilot.sh deploy
```

`access public` изменяет только режим доступа и сохраняет приватную копию настроек. Новая конфигурация применяется при `deploy`. Если менялись только настройки и образ уже соответствует исходникам, допустимо `deploy --no-build`.

Имя Compose-проекта `synapse-pilot` историческое: оно сохраняет существующую БД и не означает закрытый доступ. Не запускайте вместо него обычный `docker compose up`: `compose.yaml` предназначен для разработки.

## Управление и восстановление

```bash
bash scripts/pilot.sh status
bash scripts/pilot.sh logs backend worker
bash scripts/pilot.sh doctor
bash scripts/pilot.sh backup
bash scripts/pilot.sh stop
```

- `doctor` проверяет локальные настройки и CA, не подтверждает доступность MAX или внешнего HTTPS.
- `backup` создаёт PostgreSQL dump в `private/backups/`.
- `stop` останавливает приложение и worker, сохраняя БД.
- `deploy` не скачивает Git-изменения, не настраивает прокси и не удаляет тома.
- При ошибке миграции обновление останавливается. В журнале указывается имя миграции и SQLSTATE; автоматический откат БД не выполняется. Сохраните backup и устраните причину до повторного запуска. Не исправляйте ошибку удалением тома или правкой уже применённой миграции.
- Не меняйте пароль инициализированной БД только в env: смена пароля роли PostgreSQL должна быть согласована с настройками приложения.

Для временного закрытого стенда существует `access closed`; тогда требуется заполненный `PILOT_ALLOWED_MAX_IDS`. Режим сдачи проекта - общий доступ с настоящей авторизацией MAX.
